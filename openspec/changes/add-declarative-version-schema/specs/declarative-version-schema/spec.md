## ADDED Requirements

### Requirement: Define one authoritative declarative structural schema
The project SHALL define the structural contract of `docker-constructor.toml` in one immutable standard-library Python schema registry. The registry SHALL describe required and optional fields, primitive and container types, constants, enums, string patterns, closed tables, dynamic maps, tagged variants, model factories, and attached named semantic rules without embedding selected dependency values.

#### Scenario: Inspecting an inventory entry definition
- **WHEN** a maintainer inspects the declarative definition for a versioned entry
- **THEN** the definition SHALL identify its accepted fields, source/update variants, value formats, output model, and semantic rule names in one location
- **AND** SHALL NOT require tracing path-specific branches in the inventory loader

#### Scenario: Rejecting undeclared configuration
- **WHEN** parsed inventory data contains a missing required field, wrong type, unknown field, invalid constant, unsupported enum, or malformed patterned string
- **THEN** generic structural validation SHALL reject it with the owning TOML dot path
- **AND** SHALL use the same schema registry for static documentation generation

#### Scenario: Keeping selected values outside the schema
- **WHEN** the declarative registry or generated schema is inspected
- **THEN** it SHALL define formats and relationships only
- **AND** selected versions, revisions, artifact URLs, and digests SHALL remain sourced exclusively from `docker-constructor.toml`

### Requirement: Interpret the schema generically into typed inventory values
The resolver SHALL use a generic standard-library interpreter to validate parsed TOML against the registry and construct the established frozen typed inventory model. Ordinary structural validation SHALL not contain entry-specific path branches or a second allowed-key registry.

#### Scenario: Loading the production inventory
- **WHEN** the resolver loads the repository `docker-constructor.toml`
- **THEN** the generic interpreter SHALL validate its structure and produce the same public typed inventory values as the established inventory contract
- **AND** resulting collections and models SHALL preserve immutability

#### Scenario: Resolving tagged variants
- **WHEN** a source or update table declares a supported discriminator
- **THEN** the interpreter SHALL select the corresponding closed schema variant
- **AND** SHALL reject fields belonging only to another variant with an actionable path

#### Scenario: Detecting schema/model drift
- **WHEN** a schema output definition no longer matches its target dataclass constructor
- **THEN** schema self-validation or tests SHALL fail before inventory validation is released

### Requirement: Keep domain semantics in named rules
Cross-field relationships and domain-language validation SHALL be implemented as explicit named semantic rules referenced by the declarative schema. The schema system SHALL not introduce a general expression language for these rules.

#### Scenario: Applying a cross-field rule
- **WHEN** structurally valid data declares a release tag, artifact URL, required platform, or override policy inconsistent with related fields
- **THEN** the attached semantic rule SHALL reject the inventory with an actionable dot path

#### Scenario: Validating an override constraint
- **WHEN** an override constraint is structurally a string
- **THEN** the named constraint rule SHALL use the established dependency-free constraint parser to validate syntax and consistency
- **AND** the default-selection rule SHALL verify that the exact default satisfies the policy

#### Scenario: Encountering an unknown semantic rule
- **WHEN** the schema registry references a rule name not present in the closed semantic-rule registry
- **THEN** schema self-validation SHALL fail before any production inventory is accepted

### Requirement: Generate deterministic JSON Schema documentation
The project SHALL generate a checked-in JSON Schema Draft 2020-12 document from the authoritative Python registry. The generated document SHALL represent supported structural constraints and annotate non-representable named semantic rules without becoming a second manually maintained source of truth.

#### Scenario: Generating schema documentation
- **WHEN** `python3 docker/versions.py schema` runs twice against unchanged source
- **THEN** both executions SHALL emit byte-identical UTF-8 JSON with stable ordering and a final newline
- **AND** the document SHALL identify `schema.py` as its generated source

#### Scenario: Checking generated-schema drift
- **WHEN** `python3 docker/versions.py schema --check` runs
- **THEN** it SHALL compare canonical generated bytes with the checked-in `versions.schema.json`
- **AND** SHALL fail actionably when the artifact is missing or stale
- **AND** SHALL not modify the working tree

#### Scenario: Refreshing generated documentation explicitly
- **WHEN** a maintainer runs `python3 docker/versions.py schema --write`
- **THEN** the command SHALL replace `versions.schema.json` with canonical generated content
- **AND** ordinary validation, build, launch, and runtime setup paths SHALL never invoke this mutation

#### Scenario: Representing semantic limitations
- **WHEN** a schema node references a semantic rule that JSON Schema cannot faithfully enforce
- **THEN** the generated definition SHALL retain the rule name in an `x-semantic-rules` annotation
- **AND** documentation SHALL state that resolver validation is authoritative for semantic checks

### Requirement: Preserve offline dependency-free validation
Required schema interpretation, self-validation, generation, and drift checks SHALL use Python 3.11+ standard-library functionality only and SHALL not require Docker, network access, or an installed JSON Schema package.

#### Scenario: Running schema tests in a sanitized environment
- **WHEN** the schema unit, fixture, generation, and drift tests run with provider credentials removed and no Docker daemon
- **THEN** all required checks SHALL complete without provider requests, package installation, or external schema tools

#### Scenario: Using optional external tooling
- **WHEN** an editor or CI environment has a JSON Schema or TOML schema integration available
- **THEN** it MAY consume `versions.schema.json` for structural feedback
- **AND** absence of that tooling SHALL not prevent authoritative resolver validation

### Requirement: Preserve validator compatibility during migration
Migration to declarative validation SHALL preserve the accepted production inventory, public typed models, exception families, and actionable path behavior established by the version inventory contract.

#### Scenario: Comparing old and new validators
- **WHEN** the existing valid and invalid fixture corpus is evaluated before cutover
- **THEN** differential tests SHALL compare acceptance, rejection, exception family, and owning path between validator implementations
- **AND** intentional behavior changes SHALL require dedicated fixtures and explicit review

#### Scenario: Completing cutover
- **WHEN** differential parity and real-inventory validation pass
- **THEN** production inventory loading SHALL use the declarative interpreter
- **AND** obsolete imperative allowed-key registries and duplicated entry dispatch SHALL be removed rather than retained as competing schema sources
