## Why

Managed Pi extensions are currently selected from per-version runtime artifact catalogs, materialized on the host, mounted into each container, and installed into the mounted Pi home at launch. That model conflicts with reproducible image-owned npm closures and permits runtime overrides that cannot be represented by one reviewed lockfile.

## What Changes

- Add a reviewed managed-extension root model in `docker-constructor.toml`, reuse the required closed `[build.stages.base.node].node_version` and `.npm_version` fields owned by the prerequisite `materialize-build-artifacts-on-host`, and add one checked-in npm `package-lock.json` v3. Ordinary `validate` and `build` require the checked-in lockfile roots to match the TOML roots exactly and require a complete valid closure; the reviewed fields are the sole expected resolver/assembler toolchain versions, npm version is never inferred from the image tag, and transitive packages are never treated as user-selectable Pi package sources.
- Use `add-locked-npm-environment-assembler` to assemble the complete locked extension closure on the host before Docker build, validate its evidence, and deliver it through the immutable BuildKit named context for installation at `/opt/pi-extensions` without BuildKit npm networking or installation.
- **BREAKING** Remove managed-extension runtime artifact catalogs, host runtime materialization, per-package mounts, runtime installation/network behavior, and managed-extension runtime overrides. Changing a managed extension requires editing reviewed roots, synchronizing Constructor-managed lockfiles, reviewing the result, and rebuilding the image.
- Check managed extension root updates in ordinary `check-deps` through a dedicated version-only provider fixed to `https://registry.npmjs.org/`; compare exact roots with latest eligible stable versions, suggest only an exact root version, never inspect tarball URL/SRI or closure data, and report unavailable authority without custom-registry fallback. Add top-level `sync-lock` as the separate mutation-capable orchestration boundary for every Constructor-managed lock owner; initially the only registered owner is the managed Pi extension `package-lock.json`. `sync-lock` invokes no ordinary update provider. It runs owner preflight, generates every candidate, and fully validates every candidate before publishing any lockfile. It then publishes the complete candidate set as one durable logical transaction with recovery/rollback, so owner failure before commit changes no lockfile and interruption during a future multi-file commit cannot leave a final partially synchronized set. The managed-extension owner preflight validates the closed inventory schema, exact root declarations, the prerequisite-owned reviewed Node/npm pins, and checked-in lockfile location but deliberately does not require the existing lockfile to match newly edited TOML roots; its candidate must match those roots exactly and contain a complete valid closure. In the inventory-pinned Node image it compares `node --version` with reviewed `node_version`, then `npm --version` with reviewed `npm_version`, permits no npm resolution or resolver network access until both succeed, and runs exactly `npm install --package-lock-only --ignore-scripts --no-bin-links --no-audit --no-fund --registry=https://registry.npmjs.org/` against a temporary `package.json` rendered from reviewed exact roots. The fixed public registry, isolated npm configuration, opaque npm redirect behavior, credential-free projected inputs, candidate closure/SRI/origin validation, and byte-preserving failure semantics remain owner requirements. `sync-lock` changes no reviewed roots; success requires review and rebuild. The assembler receives the same reviewed Node/npm values only as verification inputs, installs only an already reviewed lock with `npm ci`, and never resolves or updates it.
- Register exactly one constructor-owned absolute local-path entry in `settings.json.packages` for each reviewed managed root: `/opt/pi-extensions/node_modules/<name>` for an unscoped root and `/opt/pi-extensions/node_modules/@<scope>/<name>` for a scoped root; never register the common `node_modules` directory or transitive packages. Add, update, and remove these entries idempotently through a crash-safe sidecar transaction whose active `managedEntries` records are distinct from exact user-owned `suppressedBaselines`; atomically suppress qualifying duplicate user npm entries, restore their preserved baselines when roots are removed, recover interruptions without data loss, and verify Pi actually loads each registered root and its transitive imports from the image-owned closure after reconciliation.
- Add `/usr/local/bin/pi` wrapper protection that classifies only documented Pi forms: reject Pi-agent updates, broad package updates, and recognized install/remove/update operations targeting an npm identity in the immutable build-time managed-root manifest; allow `list`, `update --models`, unmanaged canonical npm source operations, and `git:`/URL/path installs. Apply no mutation-like heuristic, alias inference, or fail-closed policy to unlisted argv forms; forward every unlisted form unchanged with signals and exit status preserved. The wrapper never reads or changes Pi settings or sidecar state, and every classified rejection explains the reviewed-root, `sync-lock`, review, and rebuild workflow.

## Capabilities

### New Capabilities
- `locked-image-owned-pi-extensions`: Defines reviewed managed roots, all-or-nothing lock synchronization, host assembly, evidence, immutable BuildKit delivery, and image-owned extension closure semantics.
- `pi-managed-extension-settings`: Defines constructor-owned Pi settings sidecar reconciliation, deterministic managed-root precedence, duplicate diagnostics, and preservation of user entries.
- `pi-managed-extension-guard`: Defines the Pi wrapper’s managed-root and self-update mutation protection while preserving ordinary Pi invocation behavior.

### Modified Capabilities
- `docker-runtime`: Replaces mounted runtime extension artifacts and launch-time installation with image-owned locked extensions and removes managed-extension runtime overrides.
- `docker-build-reproducibility`: Replaces runtime extension catalogs/overrides with reviewed roots and a checked-in lockfile, and defines synchronization/review/rebuild semantics.
- `docker-build-caching`: Builds locked managed extensions into an independent image-owned layer instead of runtime setup.
- `user-cache-storage`: Removes managed-extension runtime-artifact cache ownership while retaining only assembler-owned opaque download reuse and published assembled environments.

## Impact

Affects inventory and effective-selection schemas, the `check-deps` command, pinned npm assembly integration, Docker build contexts and layers, runtime launch vectors and entrypoint behavior, Pi settings files, the `pi` executable path, cache/cleanup contracts, documentation, and acceptance tests. This change depends on `add-locked-npm-environment-assembler`, archived `materialize-build-artifacts-on-host`, `add-durable-filesystem-transactions`, and the `check-deps` command introduced by `replace-check-updates-with-check-deps`; top-level `sync-lock` and the stronger multi-target/CAS transaction adapters it requires are owned here.
